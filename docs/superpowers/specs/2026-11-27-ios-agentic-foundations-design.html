APEX iOS Foundations

How this repo gets set up so agents can build the native app from your mocks, in pull requests that merge when CI is green, without waiting on you. Nothing here is built yet.

Why

The tooling decides how fast and how well everything after it gets built

You spent months on high-fidelity mocks with motion. Agents will turn them into a native app. Their work is only as good as the checks around it: what they can run, what they can see, and what stops them calling something done when it isn't. Filing-cabinet proved the approach. It also showed where it hurts: the simulator tests grew until an end-of-task run took over 20 minutes.

Goals

  • An agent can take a segment from mock to a merged pull request alone.
  • Every screen is checked against its mock by image, by the agent.
  • Test time is measured from day one and has a ceiling.
  • The React Native app and the iOS app share only the repo root.

Not goals

  • Accessibility: VoiceOver, Reduce Motion, larger text, audits.
  • Telemetry or analytics.
  • Accounts, server sync, TestFlight. All later.
  • Any product screen beyond one small proof.

Failure, even if it works

  • An agent says done while tests fail or a screen was never looked at.
  • The suite creeps back toward 20 minutes.
  • Work stalls waiting for you.
  • iOS tooling leaks into the React Native app, or the reverse.

How the rules stay separate

  • The root CLAUDE.md holds no rules of its own. It says which folder owns which work and that one pull request touches one side.
  • apex-ios/CLAUDE.md is @AGENTS.md plus Claude-only notes, as in filing-cabinet. apex-ios/AGENTS.md is the single copy of the iOS rules.
  • apex-rn/CLAUDE.md is today's file with one addition: the app is frozen, critical fixes only.
  • Hooks check paths. A session that only touches apex-rn/ never triggers the iOS gate.
  • Of the root .claude/ folder, only settings.json is committed. Skills, local settings and launch files stay untracked, as your global rule says.

Proving the move broke nothing

From apex-rn/: Jest, the TypeScript check and lint pass as they do today, and a clean prebuild plus a simulator build succeeds. The first install on your phone from the new folder is yours to do whenever you next reload it; the doc for it is one command. Arsenal's bootstrap for apex is updated to install in apex-rn/. Old branches such as feat/exercise-specific-fields will conflict with the move; they are stale and stay as they are.

The iOS project

Filing-cabinet's shape, started small

Logic lives in one local Swift package, ApexKit. Any module that doesn't import SwiftUI or UIKit must build for macOS, so its tests run on the Mac in seconds with no simulator. A lint rule and CI both catch a stray import. The app target is thin: an entry point and wiring.

Hooks, ported from filing-cabinet

  • Stop gate. An agent can't finish while the Mac tests fail on the Swift it changed. After three failed attempts it hands back and says so.
  • Format on edit. Every edited Swift file is formatted.
  • Guards. Generated files can't be hand-edited. Git hooks can't be bypassed.
  • Pre-commit. Lint and format check, only when iOS files are staged.

All of it has its own tests, as in filing-cabinet. Lint config, hook config and test tolerances change only with your OK.

Parallel agents don't collide

Filing-cabinet has one shared simulator. Here each checkout gets its own, named after the worktree and created on demand, and its own build folder. Two agents in two worktrees can run simulator tests at once.

Keeping it fast · option A chosen

What I meant, and whether it's the right way

You asked. "Hard cap on journeys" and "time budgets" were two names for one worry: nothing in filing-cabinet pushed back when a slow test was added. Each one cost five seconds and looked harmless. A hundred and thirteen of them cost ten minutes. So the question is what pushes back.

First, most of the saving is structural and needs no enforcement

  • Behaviour is tested on the Mac. In filing-cabinet many journeys existed to prove a behaviour. Here a behaviour test goes through the screen model and costs milliseconds.
  • One picture per state. Dark only, one text size.
  • A journey is for a flow across the real app's seams. Launch, database on disk, navigation, kill and restore. Most screens add none. I expect six to ten at cutover.

See the difference at APEX's size

Filing-cabinet's original setup at this size0
This design0
Three pictures a state, ten journeys and two audits a screenOne picture a state, journeys as setThe ceiling

A model, using rates measured on your Mac in filing-cabinet: 2.2 s a picture, 5.3 s a journey, 7 s an audit. It counts test time only, with no build. Real APEX numbers are measured in the foundation.

Drag the picture cost down and the screen count up. Two things show. A one-screen change is always quick. And at APEX's size, pictures alone approach the ceiling at 2.2 seconds each, which is why the foundation must measure and cut that cost. Half of it in filing-cabinet was a one-second wait before each picture.

Then, what pushes back when the suite grows anyway

A · A time ceiling

The gate has a ceiling on test time, set at about twice what it measures when first recorded. Every pull request shows the total, the change against main and the five slowest tests. Over 80% it warns. Over the ceiling the pull request fails until something is sped up, moved to the Mac, or removed. Raising the ceiling needs your OK.

It is checked in CI, against CI's own timings. Locally, make gate prints the same report and never fails on time.

For: measures the thing you care about. Agents can fix a breach without you.

Against: timing varies run to run. The headroom is what keeps that from tripping it.

Chosen by Ben, 27 Nov

B · An approved list

The journeys are a named list in one file, as filing-cabinet's smoke set was. Adding one needs your OK.

For: simple, and never fails by chance.

Against: it counts tests when the problem is minutes. It doesn't cover pictures. An agent that wants a new journey waits on you.

C · Rules and a report

The placement rules above, plus the timing report on every pull request. Nothing fails on time.

For: nothing new that can block.

Against: this is roughly where filing-cabinet was. Each addition looked fine on its own.

With A there is no separate count cap on journeys. Every journey runs in the gate, so each one spends from the same ceiling. I'm withdrawing "hard cap" as its own idea. Under all three, a single test that runs longer than 60 seconds fails, which stops hangs and one giant journey.

Mocks

From your export to an image the agent can check

The export lives in apex-ios/design/

Imported from ~/Desktop/Home screen redesign brief-project.zip: the demos, the phone-only pages in app/, every decision log, the build notes, the design system README, the fonts and the Explorations pages. make design-import ZIP= replaces it from a new export in one step, so the remaining screens and later changes arrive as an ordinary diff. Your export's own rules hold: only options stamped Locked count, the highest turn wins, and where a demo and a Motion tile differ the tile is right.

Reference images are generated

I rendered app/home.dc.html in headless Chrome at 390 × 844 and it came out correct. make mocks does that for every named state and commits the images. A demo's default state needs nothing more. Other states are reached by a short script that clicks the demo's own switches; the foundation proves this on one of them. A state that can't be reached that way gets a hand-captured image.

Two checks, two jobs

  • Against the mock: make compare puts the mock and the app side by side. The agent opens the image and lists it in the hand-off. This is judgement, since HTML and native never match to the pixel.
  • Against itself: the picture test fails when a screen changes from its last approved image. A changed reference is named in the commit with the reason.

Tokens

apex-ios/design/tokens.json is written from the export's design system: colours, the type scale, spacing, radii and motion timings. A committed generator turns it into Swift and colour assets. Views use only generated tokens; a lint rule rejects raw values. Nothing depends on Cadre.

Motion

  • Your three timings and every locked moment become named tokens. Views animate only with those.
  • make frames gives the agent a strip of frames to check order and timing against the Motion tile.
  • UI tests run with animations off, so motion never slows or breaks them.
  • How it feels on a phone is yours to judge. Each segment lists its moments for you in one issue. It never blocks the next segment.

Workflow

How a segment gets built and merged without you

  1. Take the next segment from apex-ios/docs/roadmap.md, the ordered list of what to build.
  2. Write its plan from the demo, the decision log and the build notes.
  3. Build it test-first. The stop gate keeps the Mac tests green throughout.
  4. Run affected and compare for every state touched, and open the images.
  5. A second agent reviews the branch. Findings are fixed.
  6. Open the pull request with the images and anything not verified.
  7. CI is green: merge it and start the next segment from main.

When an agent may merge

You approved this on 27 Nov. A pull request merges without you when all of these hold:

  • Every CI check is green. None skipped, none re-run until it passed by luck.
  • The second agent's review has passed.
  • The hand-off lists the images the agent opened, and states plainly anything it didn't verify.

It merges with a merge commit and deletes the branch. While CI runs, the next segment may start on top of the open branch.

What still waits for you

  • Any change to lint config, hook config, test tolerances or the time ceiling. That pull request stays open until you say yes.
  • Anything that touches production: the Worker, its database, secrets.
  • Force-pushes and anything that rewrites main. Never done.

Anything only you can judge, such as a gap in a mock or how a motion feels on the phone, becomes a GitHub issue labelled needs-ben with the default the agent took. Work continues on that default.

A fresh session for each segment

You asked for this on 27 Nov, to stop one long session filling up and getting worse. One segment, one session:

  • When a pull request merges, the session writes the next plan, updates the hand-off note, reports to the lead session and stops. The lead reads the report, deals with anything that needs you, and starts the next session in a new Herdr tab named for the segment.
  • The new session starts from files, never from a conversation: the design doc, the plan with its ticked boxes, and docs/superpowers/handoff.md.
  • A session also hands off mid-segment, at a task boundary, when its context is getting long.
  • Finished tabs are left for you to close. Nothing closes a tab it didn't open, and never the project's first tab.

The Herdr commands are personal tooling, so they become an arsenal skill and are not committed here. Until that exists they are written out in the hand-off note.

Crashes and backend

Decided now, built later

Crash reports

No SDK and no service. The app records Apple's own crash and hang diagnostics to a file, and one command copies them off your phone when it's plugged in. Once the app is on TestFlight, Xcode shows crashes with no code at all. Logging is Apple's logger. This is built when the app first goes on your phone, not in the foundation.

Backend

Not part of the tooling. Settled by Ben on 27 Nov: the app keeps its data in a SQL database on the phone, and the phone is the source of truth. The Cloudflare copy is a backup only, there so nothing is lost and nothing is backed up by hand. Whoop sign-in is the one critical reason the Worker exists. The tables are designed with the first screen that stores data. What that design starts from:

  • A backup only counts if it can be restored. There is no restore from the Cloudflare copy today; July's spec proposed restoring from the iCloud file backup.
  • The redesign changes the data whatever the server is: exercises keyed by ID, muscle tags, a generic cardio record, more than one session a day, a session's planned day and its real date. July's rule of no schema changes until cutover collides with that and has to be revisited.
  • Today's Worker uses one shared key. That works for you alone and has no accounts.
  • Whoop sign-in needs a server whatever else is chosen.
  • The iCloud file backup already exists and needs no account.
  • For other people without accounts, iCloud's private database is the route: each person's own iCloud is the account.

Build order

The foundation as its own stack

The plan will settle the details. This is the shape: six pull requests, each one usable on its own.

  1. Move the React Native app into apex-rn/. Root pointer file, CI limited to its folder, proof that it still tests and builds.
  2. The iOS skeleton. Project, package, Makefile, lint, AGENTS.md, an app that launches to an empty screen, Mac tests running.
  3. Hooks. Stop gate, format on edit, guards, pre-commit, with their tests.
  4. Design. The export imported, tokens.json and its generator, make mocks.
  5. One real screen, end to end. The tab bar and Home with no program: screen model, picture, one journey (the app launches to Home and the tabs switch), compare, frames, the time report and the ceiling.
  6. CI. Checks and the gate for iOS, and the skip for a merge that already passed.

Left to the builder

  • How pictures are taken, and how far the per-picture cost can come down. Target: one second or less.
  • The format of the state catalog and of the file that maps states to demos.
  • How the mock renderer drives a demo, and whether React is vendored so it runs offline.
  • Script internals, the SwiftLint rule set, CI caching.

Follow-ups, not in this work

  • The roadmap of product segments, written as the foundation finishes.
  • The table design, with the first screen that stores data.
  • A Herdr hand-off skill in arsenal.
  • TestFlight uploads, from filing-cabinet's scripts.
  • Bringing Cadre's design reference up to date from APEX's.
  • Crash capture, with the first build on your phone.

Risks

  • The design is about 90% done. Re-imports will happen, which is why import is one command.
  • Merging on green means a mistake no check catches reaches main before you see it. The review agent and the image checks are the guard, and any merge can be reverted.
  • The picture cost is unknown until measured. If it stays near two seconds, the gate needs a second CI job sooner.
